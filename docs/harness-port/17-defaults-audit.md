## Keeper decisions (a plain fix is not obvious)

| # | setting | fleet | house | why this needs the keeper, not a one-line fix |
|---|---|---|---|---|
| K1 | **`random_reply`'s platform default is unreachable through a normal covenant** | discord/signal axon-wide default 1000 (S1/S2) | `resident-covenant.mjs:64` `COVENANT_DEFAULTS.dispatch.random_reply = 0` is filled in by `normalizeCovenant` for EVERY handle, testament-set or not — there is never a "silent" covenant by the time `mcpl/route.mjs:473`'s `{ ...defaults, ...(base?.dispatch ?? {}) }` runs, so `base.dispatch.random_reply` is always an own, defined key (0, unless a testament or `!rr` set something else) and the platform's 1000 default can structurally never win the spread. Verified live (a throwaway `node -e` importing `normalizeCovenant` and reproducing the exact merge: result is `0`, never `1000`). | S1/S2's fix (setting `DISPATCH_DEFAULTS.random_reply = 1000` in discord.mjs/signal.mjs) is dead code as currently wired — it was the right value in the wrong place. A real fix means changing what "the covenant is silent" MEANS (e.g. `normalizeCovenant` would have to leave `dispatch.random_reply`/`bot_mention_budget` as a genuinely absent key, not a defaulted 0/1, when the raw testament omits them) — a change to the one normalization function every other covenant-reading module in this package depends on (`dispatch.mjs`, `!rr`'s own query reply, `applyCommandDispatchSettings`, at least 8 test files by name). The behavioural consequence is also live and real, not cosmetic: every resident being would start randomly answering unaddressed Discord/Signal messages at 1-in-1000 odds the moment this is fixed, on a system with live containers — exactly the kind of default flip that should not land inside a 60-minute defaults-audit pass. Recommend: fix in a dedicated round with its own test pass, not folded into this one. |
| K2 | **the being's default tool list is inverted** | `bot-runtime/src/bot-runtime.ts:1299` `const requestedTools = this.config.tools ?? []` — a bot with no `tools:` field in `config.json` gets **none** of the CLI/HTTP/terminal/delegate tools in `tool_configs` (secure-by-default; `bot-config.ts:411` never defaults it either) | `room-turn-tools.mjs:156` `tools = [...offeredNames]` when a testament has no `tools:` field — **every** house tool AND every platform-executor tool this room offers (`room-turn.mjs:218`'s `offeredNames`) | opposite defaults on a capability axis, not a numeric transcription slip. Flipping the house to "no tools unless the testament lists them" is the fleet-matching direction, but I could not confirm within this round's budget whether `offeredNames`/`executor.toolNames` also carries the room's SPEECH tools (`send_message`/`reply_message`) — `mcpl/discord.mjs`'s own `DEFAULT_BEING_TOOLS` comment says speech is deliberately left out of that specific allowlist, but `room-turn-tools.mjs`'s `offeredNames` is a different, broader set (`houseToolDefinitions()` plus the executor's full `toolNames`) that this round did not trace to its source. If speech rides in that same set, a naive fix would leave every testament-silent being mute, on a live system, the moment it lands. Needs the keeper (or a dedicated, traced round) to confirm the blast radius before flipping the default. |
| K3 | **autotrigger reactivation has no pacing** | `bot-runtime.ts:914,917,919`: `AUTOTRIGGER_DEFAULT_DELAY = 2000`ms, backing off ×2 up to `AUTOTRIGGER_MAX_DELAY = 300_000`ms (5 min) between reactivations | `autotrigger.mjs`'s `applyAutotriggerOnTurnClose` calls `reactivate()` synchronously, with no delay of any kind, the moment a turn closes | this is not a wrong number on an existing knob — the house's turn model (`room-turn.mjs`) is synchronous request/response with no scheduler; the fleet's delay/backoff lives inside an async `setTimeout` loop that has no house-side analogue yet.
